# リザルト画面の読み取り方式

ミニPC（省電力・24時間稼働）でランニングコストをかけずに、キャプチャボードの映像から
「誰が・どのキャラで・何位だったか」を取り出す方法の比較と、採用した設計。

## 候補の比較

| 方式 | 仕組み | 精度 | 速度・負荷 | 依存・コスト | 備考 |
|---|---|---|---|---|---|
| **固定領域の知覚ハッシュ照合（採用）** | リザルト画面は固定レイアウトなので、各列のファイター画像・順位バッジを 64bit の dHash にして、学習済みハッシュと比較 | 高（同一レイアウト・同一解像度なら数ビット差） | 1フレーム数ms。純 Go、C ライブラリ不要 | ゼロ円。最初に各キャラの画像を 1 回ずつ教える必要がある | 未知画像は Slack で `learn` して育てる |
| テンプレートマッチング（NCC） | 同上の領域に対し正規化相互相関で類似度を計算 | 高 | ハッシュより 100 倍重いが十分速い | 同上 | ハッシュで誤判定が出たときの第二段として追加可能 |
| OCR（Tesseract / RapidOCR / PaddleOCR） | 画面上の文字（ファイター名・プレイヤー名・1st/2nd）を文字認識 | 中（和文フォント・装飾文字で誤読が出る） | モデル推論で 1 フレーム 100ms〜1s。モデルファイルが数十MB | Tesseract は C ライブラリ、RapidOCR は Python/ONNX | 未登録の名前も読める点が利点だが、メンバーが固定なら名前タグも画像照合で足りる |
| 小型 CNN 分類器 | 自前で撮ったリザルト画面でキャラ分類器を学習 | 高（学習後） | 推論は軽いが学習データ作りが手間 | 学習環境が必要 | ハッシュ照合で足りるので保留 |
| クラウド Vision API | 画像を API に送る | 高 | ネットワーク依存 | 従量課金 | ランニングコストの方針に反するため不採用 |
| 手入力のみ | Slack / Web から入力 | 完全 | — | ゼロ | 常にフォールバックとして併用 |

## 採用した設計

1. **プレイヤーの特定は名前タグ。既知のタグは画像照合、初めてのタグだけ OCR**  
   リザルト画面の各列に出る名前タグは固定フォント・固定位置で描画されるので、一度見たタグは
   キャラと同じ dHash 照合で判別できる（文字を読まないので誤読ゼロ、数 ms）。
   初めて見るタグだけ OCR にかけ、読めた名前を既存プレイヤーとあいまい一致（1〜2 文字の違い、
   `o`/`0` や濁点の有無は無視）させ、該当がなければ新しいプレイヤーとして自動登録する。
   登録や事前準備は一切不要で、新人が来てもそのまま記録される。読めた時点でタグのハッシュを
   その名前で覚えるので、同じ人の OCR は 1 回きり。
   OCR が何も読めなかったタグは切り抜きを Slack に送り、`/smash learn <画像ID> 太郎` で手動登録できる。
   その試合は誤った相手に成績が付かないよう記録しない。
   読み間違いで変な名前が登録されたら `/smash rename 今の名前 正しい名前`、既存の人が二重登録されたら
   `/smash merge 重複 本来` で統合（成績を引き継いで再計算）。
   OCR エンジンは Windows 標準の Windows.Media.Ocr（追加インストール不要、日本語対応）が既定で、
   Tesseract や RapidOCR などは `[vision.ocr] engine = "command"` で差し替えられる。
2. **キャラも同じ仕組みで自動学習、順位は数字の形で判定**  
   実画面を見ると、各列の上にファイター名が英字（DONKEY KONG, MARIO）で書かれている。
   そこで名前タグと同じく「初回だけ OCR → 以後はハッシュ照合」にした。OCR 前に白い文字だけを
   切り出して黒文字・白地に変換すると、実画面の 4 列すべてが正しく読めた（DONKEY KONG / MARIO /
   FOX / BANJO & KAZOOIE）。ファイター名は英語名との最近傍で確定するので、コスチューム違いの影響も
   受けない。
   順位は大きな装飾数字で、OCR は一切読めなかった。代わりに、明るい画素の連結成分のうち
   「銀・金・銅の色で、黒い縁取りに囲まれ、数字らしい縦長の形」のものを数字として切り出し
   （月桂樹、シリーズアイコン、背後のキャラ絵や鎧を除外）、外接矩形を 8×8 に正規化した 64 bit の
   「形状シグネチャ」で照合する。位置・大きさ・列・背景に依存しないので、数字ごとに 1 度学習すれば
   全列・全人数で使える。1〜7 は実画面（2〜8 人の 7 枚）から得た値を組み込み済みで、8 だけ初出時に
   Slack の `learn <画像ID> 8` で一度教える。5 と 6 は形が近いので、最も近い数字が他の数字より
   3 bit 以上近いときだけ確定し、曖昧なら未知として学習に回す。
   結果として、最初に人が教えるのは「この画面がリザルトである」ことだけ
   （`vision teach -image shot.png -players N`）。
3. **画面種別・キャラ・順位・名前はすべて dHash 照合**  
   `smashrate.toml` の `layouts` に、人数ごとの「画面判定領域」「各列のキャラ画像領域」「順位バッジ領域」
   「名前タグ領域」をフレームに対する比率で持つ。1 フレームにつき最大 1 + 8×3 = 25 個のハッシュを計算するだけ。
4. **学習はゼロから、運用しながら**  
   最初は `smashrate vision teach -image shot.png -players 2 -chars マリオ,リンク -ranks 1,2 -names 太郎,花子` で
   スクリーンショット 1 枚から画面テンプレートとキャラ・順位・名前を登録。未知のキャラやタグが出ると
   切り抜き画像を `data/unknown/` に保存して Slack に通知し、`/smash learn <画像ID> <ラベル>` で
   登録するとその場で認識できるようになる。順位が読めて人が分かれば、キャラ不明でも試合自体は記録する。
   人が特定できない試合は記録せず通知だけ行う（誤った相手に成績が付くのを防ぐため）。
5. **人数ごとのレイアウトは実測済み（2〜8 人）**  
   パネルは常に 1 段で、2・3・5 人は中央寄せで隙間あり、4・6〜8 人は画面幅いっぱい。4 人以下は
   順位の数字がパネル右上、5 人以上はキャラ絵の上に重なる。5 人以上の細いパネルでは「1P/CP」バッジが
   名前タグの上段に移り、ファイター名はパネル幅いっぱいに書かれる。既定レイアウトはこの実測値で、
   7 枚すべてで画面判定・順位判定が通ることを確認している。
6. **チーム戦は「同順位 = 同じチーム」で判定（別レイアウト不要）**  
   チーム戦のリザルトも配置はほぼ同じで、違いは味方同士が同じ順位になること。そこで同順位の
   プレイヤーを同じチームとして記録し、同順位がなければ全員別チーム（1on1・乱闘）とする。
   時間制の乱闘で稀に同順位が出た場合もチーム戦として扱う（運用上は無視できる頻度）。
   全員同順位なら記録しない。`layouts` の `mode = "team"` は、将来配置が違う画面が出たとき
   のために残してあるだけで、既定では使わない。
7. **CPU 入りの試合は記録しない**  
   名前タグが「コンピューター2」「プレイヤー1」（名前未設定）の列があれば、その試合は
   レートに入れず通知だけ行う。そのタグのハッシュも「人ではない」として覚えるので、
   次からは OCR なしで即判定される。
8. **リザルト画面は短くても間に合う**  
   4 フレーム/秒で読み、同じ読み取りが 2 回続いた時点（0.5 秒）で確定する。OCR は
   その時点のフレームに対して行うので、画面がすぐ消えても構わない。
9. **開始画面・戦闘中の画面は使わない**  
   キャラ選択画面や戦闘中にも名前タグは出るが、必要な情報（誰が・何で・何位）はリザルト画面に
   すべて揃っていて、位置も安定しているので、リザルト画面だけを見る。戦闘中のタグは位置が動くため
   照合には向かない。将来、途中退出やストック数を拾いたくなったときに追加の画面を検討する。
10. **安定化と重複防止**  
   同じ読み取り結果が `stable_frames` 回連続したときだけ処理し、同じ画面は `cooldown_seconds` の間は再記録しない。
11. **誤認識は後から直す**  
   `/smash fix <試合ID> <名前> <キャラ>` と `/smash delete <試合ID>` で履歴を直すと、全員のレートが
   履歴から再計算される（数千試合でもミリ秒）。

## 別の Switch 本体を使うとき

読んでいるのは HDMI 出力なので、本体が誰のものでも同じように動く。注意点は次の 3 つ。

- **名前タグが未設定の本体**では「P1」「P2」のような既定表示になる。これは人として登録しない
  （本人未特定として記録を止め、Slack に通知する）。その本体の「名前」リストに各自の名前を
  作って選んでもらえば、以後は同じように自動登録される。
- **本体の言語設定**が違うと順位バッジの文字（1位 / 1st）が変わるので、その本体のリザルトで
  `vision teach` を一度通す。テンプレートは追加されるだけなので、両方の本体が共存できる。
- **出力解像度・HDR**が違うと画像の見え方が変わる。解析は 640×360 に縮小するので 720p と 1080p の
  差は吸収できるが、HDR は切っておく。閾値付近の距離は `vision test` で確認する。

## フレーム取得

ffmpeg をサブプロセスとして起動し、`-f rawvideo -pix_fmt rgb24` で生の RGB を標準出力から読む。
OS ごとのデバイス差（Windows dshow / Linux v4l2 / macOS avfoundation）は ffmpeg が吸収する。
解析は 640×360・2fps に落として行うので CPU 負荷はごく小さい。

## 調整手順

```
smashrate vision devices                       # デバイス名を確認して smashrate.toml の input に書く
smashrate vision snapshot -out shot.png        # リザルト画面が出ているときに 1 枚保存
smashrate vision regions -image shot.png -players 2
                                               # data/regions/ に各領域の切り抜きが出るので、
                                               # キャラ画像と順位バッジがぴったり入るまで layouts を調整
smashrate vision teach -image shot.png -players 4      # 「この画面がリザルト」とだけ教える
smashrate vision test -image shot.png                  # 認識結果と距離を確認
# 任意: キャラ・順位・名前を先に教えておくこともできる（OCR に任せるなら不要）
smashrate vision teach -image shot.png -players 2 -chars マリオ,リンク -ranks 1,2 -names 太郎,花子
```

`vision snapshot` は常駐中の監視プロセスが今見ているフレームを保存する（キャプチャボードを
開き直さないので、起動ロゴが写ることがない）。

## 判断を変えるとき

- 名前タグの照合が不安定（タグの背景色がポートごとに変わる等）なら、OCR が自動で再度走って同じ名前に
  あいまい一致し、新しいハッシュがその名前で追加される。手動で `learn` を繰り返す必要はない。
- OCR の誤読が多い場合は `vision ocr -image crop.png` で生テキストを確認し、`scale` を 4 に上げるか、
  `engine = "command"` で RapidOCR 等に差し替える。
- キャプチャボードの出力解像度や HDMI の色域が変わると、既存テンプレートとの距離が広がる。
  `vision test` の距離が閾値付近なら、新しい環境で `teach` し直す（古いテンプレートはそのまま残してよい）。
